Scenarios: what would it take?

Five-year scenarios (assumptions you can change)

Pick a preset or move the sliders. Every output below is recomputed in your browser by the same model THESIS.md uses (section 6b). These are scenarios, not forecasts; NEAR's price is held at $3.73, and NEAR held in the revenue wallets is custody, not burned.

SCENARIO Starting values from data/derived/metrics.json (scenario_start); presets from scenarios.json. Market cap / revenue uses today's market cap and is descriptive only.

Query behind this chart: the scenario model (pipeline/scenario_model.py; the browser runs dashboard/scenario_model.js, tested to match)
"""
scenario_model.py - a five-year scenario model for NEAR value capture, plus a reverse valuation.

The same arithmetic is implemented in dashboard/scenario_model.js for the live sliders;
tests/test_scenarios.py checks that both give identical results.

What it models (all per year, t = 1..years):
  volume      = today's all-Intents volume x (1 + volume_cagr)^t
  take-rate   = moves in a straight line from today's captured take-rate to take_bps_end by the last year
  captured    = volume x take-rate                      (USD; revenue NEAR sweeps into its revenue wallets)
  bought      = captured / today's NEAR price          (NEAR; the price is HELD CONSTANT - this is not a price model)
  issuance    = supply x inflation rate x realised factor
                (inflation 2.5%; with HSP-029 it falls in a straight line to 1.6% over hsp029_ramp_years,
                 starting hsp029_activation_years from today; the realised factor is measured supply growth / the maximum)
  custody     = last year's custody x (1 - custody_release_per_year) + bought
                (NEAR held in the revenue wallets; released NEAR returns to the float. Nothing here is a burn.)
  float       = supply - custody
Outputs: buyback / issuance, revenue / issuance (USD), float growth, market cap / revenue (today's market cap: descriptive).
"""


def inflation_rate(t_mid, hsp029, start_rate, end_rate, activation, ramp):
    """Inflation ceiling at time t_mid (years from today)."""
    if not hsp029 or t_mid <= activation:
        return start_rate
    return start_rate - (start_rate - end_rate) * min(1.0, (t_mid - activation) / ramp)


def run(start, cfg, sc):
    """start: today's values; cfg: scenarios.json top level; sc: one scenario. Returns one dict per year."""
    years = int(cfg["years"])
    take_end = start["take_bps"] if sc.get("take_bps_end") is None else float(sc["take_bps_end"])
    supply, custody = start["supply_near"], start["custody_near"]
    flt = supply - custody
    rows = []
    for t in range(1, years + 1):
        vol_year = start["volume_usd_per_day"] * 365.0 * (1.0 + sc["volume_cagr"]) ** t
        take = start["take_bps"] + (take_end - start["take_bps"]) * t / years
        captured = vol_year * take / 1e4
        bought = captured / start["price_usd"]
        rate = inflation_rate(t - 0.5, sc["hsp029"], start["inflation_rate"], cfg["hsp029_end_rate"],
                              cfg["hsp029_activation_years"], cfg["hsp029_ramp_years"])
        issued = supply * rate * start["realised_factor"]
        supply = supply + issued
        custody = custody * (1.0 - sc["custody_release_per_year"]) + bought
        new_float = supply - custody
        rows.append({
            "year": t,
            "volume_usd_per_day": vol_year / 365.0,
            "take_bps": take,
            "captured_usd": captured,
            "bought_near": bought,
            "inflation_rate": rate,
            "issued_near": issued,
            "buyback_share_of_issuance": bought / issued,
            "revenue_to_issuance_usd": captured / (issued * start["price_usd"]),
            "float_growth": new_float / flt - 1.0,
            "custody_near": custody,
            "market_cap_to_revenue": start["market_cap_usd"] / captured,
        })
        flt = new_float
    return rows


def reverse(start, cfg):
    """What would have to be true. Returns a dict of required values (all at today's NEAR price)."""
    years = int(cfg["years"])
    # issuance in the final year with HSP-029 active and supply grown by issuance only
    supply = start["supply_near"]
    issued = 0.0
    for t in range(1, years + 1):
        rate = inflation_rate(t - 0.5, True, start["inflation_rate"], cfg["hsp029_end_rate"],
                              cfg["hsp029_activation_years"], cfg["hsp029_ramp_years"])
        issued = supply * rate * start["realised_factor"]
        supply += issued
    need_usd = issued * start["price_usd"]            # captured revenue (USD/yr) for buybacks to equal issuance in year N
    vol_today = start["volume_usd_per_day"] * 365.0

    def cagr_needed(take_bps):
        need_vol = need_usd / (take_bps / 1e4)
        return (need_vol / vol_today) ** (1.0 / years) - 1.0

    mult = float(cfg["valuation_multiple_for_reverse"])
    rev_for_mult = start["market_cap_usd"] / mult
    return {
        "final_year_issuance_near": issued,
        "revenue_needed_to_offset_final_year_usd": need_usd,
        "volume_cagr_needed_at_today_take": cagr_needed(start["take_bps"]),
        "volume_cagr_needed_at_8_bps": cagr_needed(8.0),
        "volume_cagr_needed_at_gross_fee_bps": cagr_needed(start["gross_fee_bps"]),
        "multiple": mult,
        "revenue_for_multiple_usd": rev_for_mult,
        "revenue_for_multiple_x_today": rev_for_mult / (vol_today * start["take_bps"] / 1e4),
        "volume_per_day_for_multiple_at_today_take": rev_for_mult / (start["take_bps"] / 1e4) / 365.0,
    }

Buyback wallet: NEAR in and out per day

If bought-back NEAR were burned or sold, the balance would fall; a balance that only rises means the NEAR is being held.

FACT Source: sql/q30_buyback_balance_daily.sql, data/bq/q30_buyback_balance_daily.csv · Days with more than 10 NEAR leaving since 1 Jul: 2026-07-10 (total out 12,000 NEAR).

Query behind this chart
-- sql/q30_buyback_balance_daily.sql  (run with: python pipeline/bq_run.py q30)
-- title: Buyback wallet (buybacks.multisignature.near) - daily NEAR balance, inflows and outflows 1 Jul to 9 Nov 2026
-- sentence: If bought-back NEAR were burned or sold, the balance would fall; a balance that only rises means the NEAR is being held.
WITH ch AS (
  SELECT block_date, block_height, index_in_block, update_reason,
         affected_account_nonstaked_balance / 1e24 AS bal, affected_account_staked_balance / 1e24 AS staked
  FROM `bigquery-public-data.crypto_near_mainnet_us.account_changes`
  WHERE block_date BETWEEN '2026-07-01' AND '2026-11-09'
    AND affected_account_id = 'buybacks.multisignature.near'
),
d AS (
  SELECT *, bal - LAG(bal) OVER (ORDER BY block_height, index_in_block) AS delta FROM ch
)
SELECT
  block_date,
  COUNT(*) AS changes,
  ARRAY_AGG(bal ORDER BY block_height DESC, index_in_block DESC LIMIT 1)[OFFSET(0)] AS end_of_day_near,
  MAX(staked) AS max_staked_near,
  SUM(IF(delta > 0, delta, 0)) AS inflow_near,
  SUM(IF(delta < 0, -delta, 0)) AS outflow_near,
  COUNTIF(delta < -1) AS outflows_over_1_near,
  MIN(delta) AS largest_single_outflow_near
FROM d
GROUP BY block_date
ORDER BY block_date

Weekly real active accounts, four strictness levels

Each step down removes more accounts that look automated or one-off; the bottom line (engaged and returning) is our most conservative count of real users.

FACT Source: sql/q11_real_active_weekly.sql, data/bq/q11_real_active_weekly.csv · L4 (engaged and returning) is the most conservative count of real users.

Query behind this chart
-- sql/q11_real_active_weekly.sql  (run with: python pipeline/bq_run.py q11)
-- title: Weekly "real active accounts" under four stricter definitions
-- sentence: Each step down removes more accounts that look automated or one-off; the bottom line (engaged and returning) is our most conservative count of real users.
-- L1 organic: sent >=1 tx to something other than game.hot.tg or itself, not a *.users.kaiching account.
-- L2 engaged: L1 and (organic on >=2 days that week, or >=2 distinct counterparties on one day).
-- L3 returning: L1 and also L1 in one of the previous 4 weeks.
-- L4: both L2 and L3.
-- Approximation: counterparties are counted per day, not de-duplicated across the week.
WITH w AS (
  SELECT
    DATE_TRUNC(block_date, WEEK(MONDAY)) AS week,
    signer,
    COUNT(*) AS active_days,
    COUNTIF(other_receivers > 0) AS organic_days,
    MAX(other_receivers) AS max_daily_counterparties,
    LOGICAL_AND(game_txs = txs) AS game_only,
    LOGICAL_OR(ENDS_WITH(signer, '.users.kaiching')) AS kaiching
  FROM `{{project}}.{{dataset}}.signer_day`
  GROUP BY week, signer
),
l1 AS (
  SELECT *, LAG(week) OVER (PARTITION BY signer ORDER BY week) AS prev_l1_week
  FROM w
  WHERE organic_days > 0 AND NOT kaiching
),
a AS (
  SELECT week, COUNT(*) AS all_signers, COUNTIF(game_only) AS game_only_signers,
         COUNTIF(NOT game_only) AS non_game_signers
  FROM w GROUP BY week
),
b AS (
  SELECT week,
    COUNT(*) AS l1_organic,
    COUNTIF(organic_days >= 2 OR max_daily_counterparties >= 2) AS l2_engaged,
    COUNTIF(prev_l1_week >= DATE_SUB(week, INTERVAL 28 DAY)) AS l3_returning,
    COUNTIF((organic_days >= 2 OR max_daily_counterparties >= 2)
            AND prev_l1_week >= DATE_SUB(week, INTERVAL 28 DAY)) AS l4_engaged_and_returning,
    COUNTIF(REGEXP_CONTAINS(signer, r'^[0-9a-f]{64}$')) AS l1_hex_implicit
  FROM l1 GROUP BY week
)
SELECT a.*, b.* EXCEPT (week)
FROM a LEFT JOIN b USING (week)
ORDER BY week

Do new organic accounts come back?

Of the accounts first seen doing something other than the HOT game in a given week, this shows how many came back in later weeks.

FACT Source: sql/q12_retention_cohorts.sql, data/bq/q12_retention_cohorts.csv · Cohorts with fewer than 4 weeks of follow-up are left out.

Query behind this chart
-- sql/q12_retention_cohorts.sql  (run with: python pipeline/bq_run.py q12)
-- title: Weekly retention of organic accounts by first-seen week
-- sentence: Of the accounts first seen doing something other than the HOT game in a given week, this shows how many came back in later weeks.
-- Caveat: "first seen" means first seen since 1 Jan 2026, so January cohorts include older users.
WITH l1 AS (
  SELECT DISTINCT DATE_TRUNC(block_date, WEEK(MONDAY)) AS week, signer
  FROM `{{project}}.{{dataset}}.signer_day`
  WHERE other_receivers > 0 AND NOT ENDS_WITH(signer, '.users.kaiching')
),
first_week AS (SELECT signer, MIN(week) AS cohort FROM l1 GROUP BY signer),
j AS (
  SELECT f.cohort, f.signer, DATE_DIFF(l.week, f.cohort, WEEK) AS k
  FROM first_week f JOIN l1 l USING (signer)
)
SELECT
  cohort,
  COUNT(DISTINCT signer) AS accounts,
  COUNT(DISTINCT IF(k = 1, signer, NULL)) AS active_week_1,
  COUNT(DISTINCT IF(k BETWEEN 1 AND 4, signer, NULL)) AS active_weeks_1_to_4,
  COUNT(DISTINCT IF(k BETWEEN 5 AND 8, signer, NULL)) AS active_weeks_5_to_8,
  DATE_DIFF(DATE '2026-11-09', cohort, WEEK) AS weeks_observable
FROM j
GROUP BY cohort
ORDER BY cohort

Shows how much NEAR the address collected on 27 Oct and whether it was moved out afterwards.

FACT Source: sql/q21_oct27_target_balance.sql, data/bq/q21_oct27_target_balance.csv · 12,028 accounts (94% never active in 2026 before) sent it 4,072 NEAR on 27 Oct; it sent 78,677 NEAR out on 29 Oct.

Query behind this chart
-- sql/q21_oct27_target_balance.sql  (run with: python pipeline/bq_run.py q21)
-- title: 27 Oct event - daily balance of the unnamed address, 20 Oct to 9 Nov
-- sentence: Shows how much NEAR the address collected on 27 Oct and whether it was moved out afterwards.
-- Uses account_changes (balance after every change) instead of the heavy args column.
WITH ch AS (
  SELECT block_date, block_height, index_in_block, update_reason,
         affected_account_nonstaked_balance / 1e24 AS bal, affected_account_staked_balance / 1e24 AS staked
  FROM `bigquery-public-data.crypto_near_mainnet_us.account_changes`
  WHERE block_date BETWEEN '2026-10-20' AND '2026-11-09'
    AND affected_account_id = '282acb8e0fea9c3b2a87f01ba8a3eaff8447d1958adf4bdd1a81d6a7720547ef'
),
d AS (
  SELECT *, bal - LAG(bal) OVER (ORDER BY block_height, index_in_block) AS delta FROM ch
)
SELECT
  block_date,
  COUNT(*) AS changes,
  ARRAY_AGG(bal ORDER BY block_height DESC, index_in_block DESC LIMIT 1)[OFFSET(0)] AS end_of_day_near,
  MAX(staked) AS max_staked_near,
  SUM(IF(delta > 0, delta, 0)) AS inflow_near,
  SUM(IF(delta < 0, -delta, 0)) AS outflow_near,
  COUNTIF(delta < -1) AS outflows_over_1_near,
  STRING_AGG(DISTINCT update_reason) AS update_reasons
FROM d
GROUP BY block_date
ORDER BY block_date
